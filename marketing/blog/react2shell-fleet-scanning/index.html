SECURITY BRIEFING · *-2SHELL & *-4SHELL

Find every *-2Shell and *-4Shell exposure across your repositories in one scan.

React2Shell lets anyone on the internet run code on servers that use React Server Components, just as Log4Shell, Spring4Shell and Text4Shell did for Java. Each fix is a version bump. The hard part is knowing every repository and branch that still needs it. ThreatLint now answers that in one scan.

For leadership: the two-minute version

  • The risk. React2Shell (CVE-2025-55182, and CVE-2025-66478 in Next.js) lets an unauthenticated attacker take over a server with one HTTP request, scoring the maximum CVSS 10.0. 2026 added PHP2Shell, WP2Shell, Node2Shell and Java4Shell, several already exploited in the wild, and the original *-4Shell flaws (Log4Shell, Spring4Shell, Text4Shell) still linger.
  • Why it is still open. Patches shipped long ago (December 2025 for React2Shell, 2021–2022 for the *-4Shell flaws), but old versions linger in release branches, forks, side projects and apps nobody owns any more. Each one is a full server compromise waiting to happen.
  • What changed. ThreatLint's new detect-xshell scan finds *-2Shell and *-4Shell exposures in every repository and branch your GitHub and Azure DevOps access covers. It is read-only, needs no clones, and returns a list of exactly what to upgrade and to which version.
  • What to ask your team for. One fleet scan this week, every CRITICAL item upgraded and redeployed, secrets rotated where an exposed app was online, and the scan scheduled weekly.

What React2Shell is, in plain terms

React Server Components let a web server run part of a React app and stream the result to the browser. On December 3, 2025, the React team disclosed that the code that decodes those server requests could be tricked into running an attacker's instructions. No password, no click, no special access: one crafted request is enough.

Next.js applications that use the App Router inherit the flaw, because Next.js bundles React Server Components. A week later the React team fixed several related denial-of-service and source-code-exposure bugs, so “patched in December” may still mean “not fully patched”.

The *-4Shell family: same pattern, older and still out there

React2Shell joins a family of Java flaws that taught the industry this lesson first. Log4Shell (2021) turned any logged string into code execution through Log4j. Spring4Shell (2022) did the same through Spring's request data binding, and Text4Shell through Apache Commons Text. Years later they still turn up in vendored jars, legacy services and long-lived release branches, so the same scan now checks for them too.

Impacted, even when there is no fix

Some affected release lines will never get a patch: end-of-life Node.js and PHP versions, non-LTS JDKs, and Spring 5.1 and older. ThreatLint still reports them, marked No fix on this line, so you know you are exposed and that the remedy is moving to a supported release rather than waiting for one.

Why one dashboard is not enough

Most teams patched their flagship app within days. The exposure that remains sits where nobody is looking: a release/2025.11 branch that still deploys, a marketing microsite built on a starter template, a fork in a different organization, an Azure DevOps project from an acquisition. Dependency alerts usually watch default branches of repositories someone enrolled. Attackers do not limit themselves the same way.

What ThreatLint now does

detect-xshell is a new ThreatLint scan with two parts. A deterministic detector reads JavaScript, Java and Python lockfiles and builds, plus pinned runtime versions (Dockerfiles, .nvmrc, CI setup actions, WordPress core), and compares them with a vendor-verified advisory catalog, so the same input always gives the same answer. A specialist agent, appsec-xshell-detector, then confirms the result in source code and writes the remediation plan.

  • Your whole estate or a slice of it. Every source you have connected, every repository those credentials can read, and the default branch, all branches, or patterns such as release/*.
  • Fast and light. The scanner lists the file tree and downloads only package.json, npm/Yarn/pnpm/Bun lockfiles, pom.xml and Gradle files. Vendored jars such as log4j-core-2.14.1.jar are spotted by name without downloading them. Thousands of branches are practical.
  • Honest confidence. A version pinned in a lockfile, a vendored jar or a direct Maven dependency is Confirmed. An unpinned range, or a missing exploit precondition such as Spring without WAR packaging, is Plausible. An affected Next.js version with no App Router is Theoretical: still upgrade it, but it is not reachable as built.
  • Fits existing workflows. Reports use the standard ThreatLint format, so CI gates, SARIF code scanning and issue creation work unchanged.

How to run it

Pick whichever entry point your team already uses. All four run the same scanner.

  1. In the ThreatLint Workbench

    Open app.threatlint.dev, then go to Test → *-Shell exposure.

    1. Tick the connected sources to include, or All connected sources.
    2. Choose All repositories this credential can access, or search and select specific ones.
    3. Choose Default branch, All branches, or list branches such as main, release/*.
    4. Select Scan for *-Shell exposure. Progress and results stream in, each labelled 2Shell or 4Shell (and No fix on this line where that applies); download the JSON or Markdown report when it finishes.

  2. From the command line

    # One checkout
threatlint detect-xshell scan --path .

# Every repo and branch your GitHub and Azure DevOps logins can read
threatlint detect-xshell fleet --all --branches all --output xshell-report.md

# A subset: wildcards work for repositories and branches
threatlint detect-xshell fleet --repo "acme/*" --repo "Payments/checkout-web" --branches "main,release/*"

# Fail a pipeline on confirmed critical exposure (detect-2shell / detect-4shell are aliases)
threatlint detect-xshell scan --path . --fail-on CRITICAL

    Credentials come from your existing logins: threatlint github login (or GH_TOKEN) and threatlint ado login.

  3. In CI

    The AppSec Detect *-Shell GitHub Actions workflow (and its Azure Pipelines twin) runs when lockfiles, builds, Dockerfiles, runtime version files or vendored jars change, and weekly. To sweep the fleet, open Actions → AppSec Detect *-Shell → Run workflow and set fleet to true.

  4. From an AI assistant over MCP

    Connected assistants can call start_xshell_scan, then get_xshell_scan for results. Starting a scan requires explicit confirmation.

Reading the results

The report opens with a one-line risk level and a short list of targets that need action, each with the installed version and the version to upgrade to. Below it, every finding cites the exact lockfile line, the CVEs, and an acceptance check your engineers can verify.

Questions leaders should ask this week

  1. Have we scanned every repository and branch we deploy from, including acquired and archived-but-live apps?
  2. Which internet-facing apps ran an affected version while it was public (React2Shell since December 2025, the 2026 PHP, WordPress, Node.js and Java flaws since their disclosure, Log4Shell, Spring4Shell and Text4Shell since 2021–2022), and have their secrets been rotated?
  3. Is the scan scheduled, so new repositories and branches are checked without anyone remembering to?

How your data is handled

The scan is read-only. It uses the credentials you have already connected, downloads only manifests, lockfiles, build files and runtime version files, never clones or stores source code, and never sends traffic to your live applications. Tokens stay in memory and are never logged or returned. To measure the program, the ThreatLint server keeps aggregate counts only (scans run and exposures found, with no repository names, paths or credentials). That data is never exposed through the app, and operators can turn it off.
