SECURITY BRIEFING · REACT2SHELL

Find every React2Shell exposure across your repositories in one scan.

A CVSS 10 flaw lets anyone on the internet run code on servers that use React Server Components. The fix is a version bump. The hard part is knowing every repository and branch that still needs it. ThreatLint now answers that in one scan.

Amelio Wright, MBAConnect on LinkedIn ↗ November 28, 2026 · 6 min read

For leadership: the two-minute version

  • The risk. React2Shell (CVE-2025-55182, and CVE-2025-66478 in Next.js) lets an unauthenticated attacker take over a server with one HTTP request. It scores the maximum CVSS 10.0.
  • Why it is still open. Patches shipped in December 2025, but old versions linger in release branches, forks, side projects and apps nobody owns any more. Each one is a full server compromise waiting to happen.
  • What changed. ThreatLint's new detect-2shell scan checks every repository and branch your GitHub and Azure DevOps access covers. It is read-only, needs no clones, and returns a list of exactly what to upgrade and to which version.
  • What to ask your team for. One fleet scan this week, every CRITICAL item upgraded and redeployed, secrets rotated where an exposed app was online, and the scan scheduled weekly.

What React2Shell is, in plain terms

React Server Components let a web server run part of a React app and stream the result to the browser. On December 3, 2025, the React team disclosed that the code that decodes those server requests could be tricked into running an attacker's instructions. No password, no click, no special access: one crafted request is enough.

Next.js applications that use the App Router inherit the flaw, because Next.js bundles React Server Components. A week later the React team fixed several related denial-of-service and source-code-exposure bugs, so “patched in December” may still mean “not fully patched”.

Why one dashboard is not enough

Most teams patched their flagship app within days. The exposure that remains sits where nobody is looking: a release/2025.11 branch that still deploys, a marketing microsite built on a starter template, a fork in a different organization, an Azure DevOps project from an acquisition. Dependency alerts usually watch default branches of repositories someone enrolled. Attackers do not limit themselves the same way.

What ThreatLint now does

detect-2shell is a new ThreatLint scan with two parts. A deterministic detector reads lockfiles and compares resolved versions with a vendor-verified advisory catalog, so the same input always gives the same answer. A specialist agent, appsec-2shell-detector, then confirms the result in source code and writes the remediation plan.

  • Your whole estate or a slice of it. Every source you have connected, every repository those credentials can read, and the default branch, all branches, or patterns such as release/*.
  • Fast and light. The scanner lists the file tree and downloads only package.json files and npm, Yarn, pnpm or Bun lockfiles. Thousands of branches are practical.
  • Honest confidence. A version pinned in a lockfile is Confirmed. A range with no lockfile is Plausible. An affected Next.js version with no App Router is Theoretical: still upgrade it, but it is not reachable as built.
  • Fits existing workflows. Reports use the standard ThreatLint format, so CI gates, SARIF code scanning and issue creation work unchanged.

How to run it

Pick whichever entry point your team already uses. All four run the same scanner.

  1. In the ThreatLint Workbench

    Open app.threatlint.dev, then go to Test → 2Shell exposure.

    1. Tick the connected sources to include, or All connected sources.
    2. Choose All repositories this credential can access, or search and select specific ones.
    3. Choose Default branch, All branches, or list branches such as main, release/*.
    4. Select Scan for 2Shell exposure. Progress and results stream in; download the JSON or Markdown report when it finishes.

  2. From the command line

    # One checkout
threatlint detect-2shell scan --path .

# Every repo and branch your GitHub and Azure DevOps logins can read
threatlint detect-2shell fleet --all --branches all --output 2shell-report.md

# A subset: wildcards work for repositories and branches
threatlint detect-2shell fleet --repo "acme/*" --repo "Payments/checkout-web" --branches "main,release/*"

# Fail a pipeline on confirmed critical exposure
threatlint detect-2shell scan --path . --fail-on CRITICAL

    Credentials come from your existing logins: threatlint github login (or GH_TOKEN) and threatlint ado login.

  3. In CI

    The AppSec Detect 2Shell GitHub Actions workflow (and its Azure Pipelines twin) runs on lockfile changes and weekly. To sweep the fleet, open Actions → AppSec Detect 2Shell → Run workflow and set fleet to true.

  4. From an AI assistant over MCP

    Connected assistants can call start_2shell_scan, then get_2shell_scan for results. Starting a scan requires explicit confirmation.

Reading the results

The report opens with a one-line risk level and a short list of targets that need action, each with the installed version and the version to upgrade to. Below it, every finding cites the exact lockfile line, the CVEs, and an acceptance check your engineers can verify.

Questions leaders should ask this week

  1. Have we scanned every repository and branch we deploy from, including acquired and archived-but-live apps?
  2. Which internet-facing apps ran an affected version after December 4, 2025, and have their secrets been rotated?
  3. Is the scan scheduled, so new repositories and branches are checked without anyone remembering to?

How your data is handled

The scan is read-only. It uses the credentials you have already connected, downloads only package manifests and lockfiles, never clones or stores source code, and never sends traffic to your live applications. Tokens stay in memory and are never logged or returned. To measure the program, the ThreatLint server keeps aggregate counts only (scans run and exposures found, with no repository names, paths or credentials). That data is never exposed through the app, and operators can turn it off.
